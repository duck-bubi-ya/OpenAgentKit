终态到了再存
两个状态，同一次写入

session.status_idled 和 session.status_terminated 都表示会话进入终态。这时才把会话正文写入本地表。通知里没有正文，服务器再调用列出事件的接口去取。

  1. 01通知必须在几秒内回复，不能边拉边写
  2. 02同一条消息后来会变，所以要更新，不能只插入一次
  3. 03单条正文过大就不写这一行，任务标失败，不切短
  4. 04正在回复、工具审批，仍然看云上，不看这张表

依据是百炼 Webhook 契约、列出 Event 的接口，以及当前 Kit 的发送和打开链路。这是方案说明，不是已经做完的功能。

判定

方向可用，写入要拆开

落库只认这两个终态，动作相同。运行中不写。把 GET /sessions/{session_id}/events 的结果直接在回调请求里插入，会在大会话上超时、把数据库锁住。

建议形态。回调只验签、记下要拉哪个会话，立刻返回成功。后台再一页一页拉消息，按消息 id 更新。太大的一行不写，任务标失败。
01 — 结论

这张表只存终态副本

用户还在看模型打字时，页面继续走现在的实时流。表里的内容在会话进入终态之后写入。它用来留底、重启后回看，不用来决定能不能发消息、能不能点允许。

现在

打开就向云上要

聊天正文在内存里。人走了就丢。本地 kit_sessions 只有封面、状态和文件编号。

加上之后

终态到了再写

收到 status_idled 或 status_terminated，拉已完成的事件，按消息编号写下或覆盖。两个事件做同一件事。

运行中

实时流继续看云上

模型正在输出时，这次回复还不在表里。页面继续读实时流。工具审批也看云上。

02 — 接口

三个接口各自给什么

方案用到百炼文档里的三块。它们的分工要先分开，否则容易把「通知」当成「正文」。

接口实际拿到的东西在这个方案里的角色
Webhook 回调 一个很小的信封：事件编号、时间、资源编号、事件类型。会话类通知的 data.id 是会话编号。没有用户说的话，也没有模型回复。 门铃。告诉 Kit「这个会话进入终态了」。
Webhook 管理 创建、查询、启停、测试、重置签名密钥。密钥只在创建和重置时出现一次。每个工作空间最多 20 个端点。 服务启动时创建端点。密钥只写入数据目录，不进仓库，也不进消息表。
GET /sessions/{session_id}/events 已经说完的消息列表。每页最多 100 条，用 next_page 翻下一页。接口不返回一共多少条。字段包括消息编号、角色、类型、内容、时间。 真正的正文来源。终态到达之后由后台去拉，不是回调请求自己去拉。
文档里的限制要直接写进设计。 回调要在 5 秒内返回。返回 200 到 299 才算成功，平台不再重试。同一条通知可能投递多次，外层编号不变。顺序不保证。事件记录只留 7 天。私网地址不能当回调。这些都决定了不能在回调函数里翻完一个大会话再插入。

什么时候才存

百炼没有「来了一条聊天消息」这种通知。写入只认会话结束：session.status_idled 和 session.status_terminated。两个名字是同一件事，都表示这一轮已经跑完。收到哪一个，都给这个会话排一条任务，分页把已经说完的消息按 id 写入或更新。后到的终态可以再盖一次，不会把上次写下的内容冻住。

用户之后又发消息，会话会重新运行。再次进入这两个终态之一时，再写一次。运行过程中不写。

事件收到后做什么
session.status_idled终态。把这个会话放进同步队列，写入正文。
session.status_terminated终态。和上面同一件事，同一条队列，同一种写入。
session.thread_idled、session.thread_terminated子线程自己的终态。并进同一个会话的队列。和主会话终态短时间连着到，合并成一次拉取。
session.deleted、session.archived验签后回复 200，不入队。清消息走 Kit 自己的删除事务，不另做清理任务。
其他 20 多种资源事件验签后直接回复成功，不入库。智能体、环境、密钥库的变更和聊天正文无关。
03 — 主流程

回调只入队，调度器再写正文

评审先看这三句。 一个 webhook_id 对应一条任务，同一个号再来不再插入。任务里不放聊天正文，只记要拉的会话、任务状态，以及拉到哪一页。当前版本全局同时只跑一条，先到的先领；同一个会话已经有一条还没开始的任务时，新通知挂到那一条上，只拉一次。

任务表就是队列，前面不再放一个单独的队列。Webhook 把终态任务写进 kit_session_message_jobs，马上回复百炼。调度器领到任务后，分页调用 GET /sessions/{session_id}/events，按消息 id 写入 kit_session_messages。每一页写完再要下一页。全部页都成功，并且这个会话没有更新的任务插进来，才删掉这次列表里已经没有的本地旧行。中途失败或单条过大，已写下的页留下，旧行先不删。删除会话时清消息，走现有删除事务，不进这个队列。

步骤谁做做什么动哪张表
1回调读原始 body，用数据目录里保存的 Signing Secret 验签。时间差超过 5 分钟，或签名不对，直接拒绝，不建任务。不写
2回调解析信封。不是上面的终态，回复 200，到此结束。删除和归档也不入队。不写
3回调按 webhook-id 插入一条任务。这个编号已存在，说明是同一次投递的重试，回复 200，不新增工作。jobs
4回调同一会话如果已经有一条还没开始的同步任务，新任务标成合并，挂到那一条上。不排第二次全文拉取。jobs
5回调任务行提交成功就返回 200，并叫醒调度器。任务写不进去才返回 500，让百炼按 10 秒、30 秒、1 分钟重试。jobs
6调度器领一条到期的任务。同一会话已有任务在跑，就先领别的会话；没有别的，就等。jobs
7调度器对照 kit_sessions 和删除进度。不是 Kit 的会话，或删除还没定论，任务标跳过，不建消息行。jobs
8调度器分页 GET。一页最多 100 条，接口不返回总数。按消息 id 插入或更新，提交后再要下一页。page_token 记下一页，pages_written 记已经写了几页。messages
9调度器页全部成功，且没有更新的任务插队，任务标 succeeded，并删掉云上这份列表里已经不存在的本地行。失败或超限则任务标 failed，已写的页保留。jobs、messages

同一条消息要覆盖

列出事件的接口给出的是完成后的消息。同一次运行里，工具调用和工具结果可能分属前后两次终态。后一次 status_idled 或 status_terminated 到达时，必须用同一个消息编号盖掉旧行。只插入、冲突就跳过，会把半成品永远留在库里。

04 — 调度器

一个循环，一次一个会话

调度器跑在现有 Kit 服务进程里，和 Hono 一起启动、一起停。默认关闭：管理端还没保存回调地址，或还没取得签名密钥时，循环不启动。回调地址仍登记在接口里，请求得到 404。任务表就是队列。不使用 cron，不另起进程，也不扫 kit_sessions 找该同步谁。

1 回调

只负责入队

验签，往任务表插一行，叫醒循环，立刻 200。这一步不拉消息，不写消息表。

2 循环

决定何时动手

被叫醒或每隔约 2 秒看一次任务表。全局同时只跑一条。正在跑时再来通知，只记一个标记，当前这一页写完再看。

3 执行

拉一页，写一页

领到任务后分页调用列出事件。云上那一页先放在内存里，短事务写入消息表，再要下一页。写库的时候不去等云上。

放在现有进程的哪里

块建议放在这一块做
回调路由 apps/server/src/routes/webhooks.ts，在 app.ts 里挂上，并加入公开路径 读原始 body 验签。终态才插任务。路径建议 POST /api/kit/webhooks/bailian。现有中间件会向其他 /api 要成员身份，这个地址必须公开，否则百炼进不来。
调度循环 apps/server/src/schedulers/session-message-scheduler/ 类 SessionMessageScheduler，对外只有 start、stop、wake。启动时调用构造时传入的回收，之后一次只跑一条。领取和写入由传入的函数完成，不在这个目录里写 SQL。测试里创建应用时不调用 start。
执行一条 同一个 service 里的函数，不另开文件进程 分页拉取、按消息 id 写入、记 page_token 和 pages_written、收场。一条任务跨很多页时状态保持 running，每页提交一次。
两张表 store/session-message-jobs.ts、store/session-messages.ts 领取、合并、翻页、写入都走 store。路由和循环不直接拼 SQL。
拉云上消息 现有 gateway 旁边加一个「转换前」的读取 现在的 gateway.listEvents 会先把云上消息收成 Kit 的 SessionEvent，object 和 status 会丢掉。落库要的是列出接口返回的那一项，所以在 toContractEvent 之前把 data[] 交出来。发送和 stream 继续用现在的转换。
和现有两套东西分开。 kit_operations 是人工确认后的高风险操作，这条链路不往那里插任务。实时流的内存缓冲继续只服务打开对话，调度器不往那个缓冲里写。

一条任务在循环里怎么走

醒：wake，或约 2 秒到了，或进程刚启动
若上一次执行还没结束：只记下「还要再看」，不并行开第二条
领取：一个事务里把一条 queued 改成 running，写 lease_until
对照目录：不是 Kit 的会话，或删除还没定论 → skipped，本轮结束
拉一页：HTTP 在事务外面。一页最多 100 条，接口不返回 total
写一页：短事务按消息 id 插入或更新，记下 page_token、pages_written
还有下一页：继续拉，状态仍是 running
没有下一页，且没有更新的任务：succeeded，并删掉这次列表里没有的本地旧行
失败或超限：已写的页留下，旧行先不删

进程在两页之间死掉时，任务还是 running。下次启动看到 lease_until 已过，改回 queued，有 page_token 就从那一页继续。第一版只有一个进程，不用多台机器抢同一行。

什么时候醒

时机做什么
回调刚写入任务进程内打一个信号，循环马上看一眼队列。不等下一个时钟。
固定短间隔建议 2 秒看一次。用来捡重试到期的任务，以及上次进程崩溃后租约过期的任务。2 秒是建议值，不是百炼的要求。
进程启动把 running 且 lease_until 已过的任务改回 queued。有 page_token 的从那一页继续，没有的从头拉。覆盖写入可以重做已写过的页。

怎么领任务

在一次数据库事务里完成领取，避免同一次循环领走同一条：

选出一条 status = queued、available_at 已到的任务
条件：这个 session_id 没有另一条 status = running
排序：created_at 升序，先到先领
改成 status = running
lease_until = 现在 + 2 分钟
generation = 该会话已有任务的最大 generation + 1

当前版本全局同时只领 1 条，按插入时间先到先领。SQLite 是单写入，拉取时还会占着云上接口。同一个会话不会有两条任务一起写。以后若要并行，也只能是不同会话同时拉，并且要单独看云上的限流。第一版不并行。

同一个会话的任务怎么并

当时队列里有什么新的终态通知到达
这个 webhook_id 已经有行不插入。这是同一次投递的重试。
已有一条 queued 的同步任务新行写成 merged，merged_into_job_id 指向那条还没开始的任务。那条任务改记最新的通知编号和事件类型。全文只拉一次。
已有一条 running新行保持 queued。正在跑的任务写完时如果同会话已有更大的 generation，不删「自己没看到」的消息。循环接着领这条新任务，再拉一遍。
上一次已经 succeeded这是新的终态，新建 queued。再写一遍，按消息编号覆盖。

任务跑完怎么收场

结果任务状态消息表要不要再跑
每一页都写完，且没有更新的任务succeeded覆盖写入，并删掉这次列表里没有的旧行不再跑，直到下一次终态
云上 5xx、超时、连接失败，次数未到改回 queued，available_at 推后已写的页保留建议最多 4 次，间隔 10 秒、30 秒、1 分钟
次数用完，或单会话超过 8MBfailed已写的页保留，不删旧行不再自动跑。下一次终态会新建任务
会话不属于 Kit，或删除进行中skipped不改不跑
租约只防进程崩溃。 任务开始时写 lease_until。正常做完会自己改状态。进程中途死掉，启动时只回收过期租约。第一版只有一个进程，不需要多台机器抢同一行。

调度器不进入发送消息、打开 stream、工具审批。那三条链路继续直接访问云上。任务失败只影响本地副本是否完整，不影响用户能不能接着聊。

05 — 表

新建两张表

任务表回答「还要不要拉、拉到哪一页、这次拉完没有」。一行是一次通知，里面是 webhook_id、session_id、任务状态和翻页位置，不放聊天正文。正文表回答「这句消息是什么」。一个会话有多少条、一共多少字节，从正文表按 session_id 汇总。不另建进度表。两张表都不改 kit_sessions 的列。

表一行是什么谁写
kit_session_message_jobs一次通知对应的一条任务。只记拉哪个会话、状态、拉到哪一页回调插入，调度器更新状态
kit_session_messages一条已完成的消息只有调度器
进度表不建。 正在跑看有没有 status = running 的任务。这次拉完没有看该任务是 succeeded 还是 failed。消息条数和会话总字节从 kit_session_messages 汇总。
不存的东西。 Webhook 信封原文、签名密钥、会话 GET 的 attributes、请求头、文件字节。next_page 和 request_id 属于整页，翻页位置在任务表。密钥放在数据目录，不进这两张表。
06 — 边界

这些情况要事先定规则

正文很大

这是最需要先定的。一条工具输出、一份贴进来的长文，都可能比普通聊天大几个数量级。SQLite 是一个文件、同一时间适合一个写入。一条几兆的插入会卡住成员、限额、会话目录这些本来很快的写入。

层级建议超过之后
单条消息 单条 content 加 metadata 超过 256KB 时，这一行不写入。256KB 是保护线，不是接口限制。 任务标 failed。这一行不写。云上仍有原文。
单个会话 已存正文合计不超过 8MB。 停止再写这个会话的新行，任务标 failed。已经原样写好的留下。聊天仍走云上。
一次拉取 一页写一次，写完释放内存。不要先把所有页拼成一个大数组。 页数或总时间超过预算，任务标 failed，下一次终态再从已成功的页之后继续。游标重复则停止并记错误，避免死循环。

回写的一行必须是完整消息。超限就停，不改 content。用户正在看的实时回复不经过这张表。

同一声门铃响了好几次

百炼明确说同一事件可能投递多次，外层 id 不变。kit_session_message_jobs.webhook_id 是唯一键。第一次已经排队或跑完，后来的请求验签后直接 200。

这和「会话再次进入终态」不同。新的终态会带来新的通知编号，必须再同步。去重的是同一声门铃，不是这个会话永远只抄一次。

通知乱序

后发生的终态可能先到。status_idled 和 status_terminated 不保证谁先谁后，处理办法相同：同一个会话的同步串行，新任务把 generation 加一。旧任务结束时发现编号已经变了，就退出，不把状态改成完整。拉取本身拿的是「现在云上有哪些已完成消息」，不是「门铃响起那一瞬间的快照」。所以晚到的旧门铃如果还去拉，拉到的也是更新后的列表。危险的是旧任务用一份旧列表去删除「它没看到的新消息」。规则是：只有同一次任务从第一页拉到最后一页都成功，才允许删掉本地有、云上这份列表里没有的消息。不完整的任务只覆盖自己写下的编号，不删除。

等待工具审批

还没收到 session.status_idled 或 session.status_terminated 时，不写这张表。审批按钮仍然看云上当前待办。若平台在等待批准时已经投递了其中一个终态，这次写入的是当时已经完成的消息。用户点允许或拒绝之后，会话会再跑一遍，再次进入终态时用同一个消息编号覆盖。

不是 Kit 建的会话

一个工作空间的 Webhook 会收到这个空间里所有会话，包括控制台或其他系统建的。Kit 只处理 kit_sessions 里有的编号。没有的直接跳过，不新建目录，也不建消息行。否则会把别人的对话写进这个库，还不知道属于哪个用户。

删除会话

成员删除会话时，现有流程会先封存用量，再删 kit_sessions。消息行放在同一次提交里删掉。这不是调度任务。

若回写已经在拉，写之前再查一次目录。行已经不在，或删除还没定论，就放弃这次写入。云上的 session.deleted、session.archived 只回复 200，不入队，也不把会话重新插回 kit_sessions。

回调地址和密钥

百炼要求回调是它能访问的公网地址，私网和本机地址不行。本地 pnpm dev 默认没有这个地址，所以这个能力必须默认关闭。管理员在管理端「配置」页填写部署这台服务的公网 IP 加端口，或映射到该服务的域名。回调地址只在这一页维护。

验签要用创建时那一次给出的 Signing Secret。服务首次启动时创建 Webhook，把密钥写入数据目录，同一回调地址之后直接复用。之后再查 Webhook 不会带回密钥。日志、错误、审计详情都不能出现密钥和消息正文。

服务器重启或开了多份

现在的设计是一台服务器配一个 SQLite 文件。任务表因为在库里，重启后可以接着跑。如果同一套库后面挂了多台服务器，两台可能同时收到门铃、同时写。在改成共享队列之前，只允许一台处理回调。这和现有「先不要水平扩容」是同一条限制。

列出接口和实时流不是同一种形状

打开对话时，实时流里同一条消息会从「正在写」变成「写完了」。列出接口的文档写的是历史消息，状态为已完成。所以这张表在终态到达后存写完的结果，不录制打字过程。实施时要用一条真实会话对一下：终态之后列出的消息编号，是否和页面上最终看到的编号一致，工具结果在不在。对不上就先不要让页面读这张表。

07 — 影响

先做写入，打开对话的路径先不动

如果这一期只在终态到达后写入，用户看到的聊天不会变快，也不会变。变的是磁盘上多了一份终态正文，以及服务器多了一个公网入口。

现有位置这一期
apps/server/src/routes/kit.ts 的发送和 stream 不改。发送仍是 POST /api/kit/sessions/{id}/messages，再转到云上 POST /sessions/{id}/events。回复仍从 stream 来。
apps/server/src/services/session-streams.ts 不改。打开对话仍向云上要历史。等副本被证明和云上一致之后，才单独讨论终态副本能不能先读本地。
apps/server/src/store/sessions.ts 不把正文塞进 kit_sessions。目录表继续只放封面。新表用会话编号去对目录。
apps/server/src/services/session-deletion.ts 和 store/session-usage.ts 删目录行时一起删消息行。用量数字仍留在用量表。
新建回调路由、进程内调度器、两张表的迁移 这是这一期的代码。默认关闭。
体验页 apps/web 这一期可以没有界面变化。页面还不读这张表。
和现有规矩的关系。 现在写明聊天正文不进本地库，云上是这份内容的原件。这张表是有意加的副本，默认关闭，不参与发送和审批。要做的话，得把这条例外写进设计说明，不能当成普通加表。

做完能得到什么，还得不到什么

结果
能会话进入 status_idled 或 status_terminated 之后，本地有一份可查询的消息副本。服务器重启也不会丢这份额外副本。企业可以在自己的机器上备份这个库。
部分单条超过保护线的消息这一行不写，任务标失败。单个会话超过保护线就停写新行，已经写好的留下。等待审批时如果已经收到终态，这次写下的是当时已经说完的消息，用户点完之后，下一次终态再按消息 id 更新。
不能不能靠这张表看正在打的字。不能在百炼宕机时继续发消息。不能把副本当成审批依据。本地开发如果没有公网地址，收不到门铃，表会一直是空的。
08 — 还要定

评审时需要拍板的几件事

事项建议不拍板的后果
单条和单会话的大小上限 超限的处理已经定了：这一行不写，任务标失败，不切短。数字先用单条 256KB、单会话 8MB，做成配置。评审确认这两个数。 一条工具输出就能把库文件和备份变成消息仓库。
会话删了，正文删不删 和目录行一起删。用量数字继续保留。若企业要留底，那是另一条保留策略，不要和默认删除混在一张表的隐含行为里。 删除后库里还留着对话，和现在的删除预期不一致。
谁可以读这张表 这一期不给页面读。以后读，也只允许会话目录里的同一个 subject_id。 后台接口如果少一次归属检查，就会串读别人的正文。
每次终态是否总是从头拉 第一版按消息编号覆盖，完整成功后才删除云上已不存在的本地行。先不要用「只拉上次时间之后」省略旧消息，避免后一次终态补上的内容被漏掉。 长会话每次终态都从头拉，成本高。这是已知代价。等对过真实数据，再加「旧消息不再变化」的增量。
默认开不开 关。只配置了百炼能访问的公网回调地址才开，密钥由创建 Webhook 写入数据目录。 开源安装和本机开发会启动一个永远收不到通知的功能，或者把密钥写进仓库。

流程、两张表和「超限不切短」已经写进这篇方案。评审若没有改口，再按这个顺序开工：两张表和验签入队、进程内调度器、分页按消息 id 更新、大小上限、删除时一起清。页面改读本地正文单独做，并且要先拿一条真实会话对比云上的列出结果。

对照文档：Webhook、回调契约、列出 Event。Kit 侧对照的是当前发送、stream 和 kit_sessions 的实现。256KB 与 8MB 是建议保护线，不是实测出来的会话大小。
